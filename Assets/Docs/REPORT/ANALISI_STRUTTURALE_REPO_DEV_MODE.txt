2. PATTERN ARCHITETTURALI
-------------------------

2.1 Service Locator Pattern ⭐⭐⭐⭐⭐
- Implementazione: ServiceContainer con lazy initialization thread-safe
- Stato: ✅ Eccellente
- Caratteristiche:
  * Inizializzazione garantita
  * Late binding implementato (10+ componenti)
  * Race conditions risolte
  * Pattern consistente

2.2 Dependency Injection ⭐⭐⭐⭐
- Implementazione: ServiceContainer.Get<T>() per servizi core
- Stato: ✅ Buono
- Metriche:
  * 44+ occorrenze ServiceContainer.Get
  * 75 occorrenze FindObjectOfType (da ridurre)
  * Accoppiamento debole per sistemi core

2.3 Singleton Pattern ⭐⭐⭐
- Implementazione: Mista (alcuni legacy, alcuni ServiceContainer)
- Stato: ⚠️ Migliorabile
- Problemi:
  * AppRoot ancora singleton classico
  * PlantDatabase usa singleton pattern
  * EventSystem parzialmente migrato
- Raccomandazione: Completare migrazione a ServiceContainer

2.4 Observer Pattern ⭐⭐⭐⭐⭐
- Implementazione: EventSystem centralizzato + C# events
- Stato: ✅ Eccellente
- Caratteristiche:
  * Event queue per gestione asincrona
  * Eventi con/senza parametri
  * Gestione errori nei listener
  * Debug info disponibile

2.5 Factory Pattern ⭐⭐⭐⭐
- Implementazione: ItemFabric, altri factory
- Stato: ✅ Buono
- Note: Alcuni metodi statici (difficili da mockare per test)

- Responsabilità: Gestione ciclo gioco, azioni giornaliere, economia

- Responsabilità: Comunicazione tra sistemi via eventi

  * Classe molto grande (700+ righe)

⚠️ PROBLEMI CRITICI IDENTIFICATI
=================================

🔴 PRIORITÀ ALTA

1. FINDOBJECTOFTYPE ECCESSIVO
------------------------------
Situazione:
- 75 occorrenze in 50 file
- ~35 occorrenze in file operativi (non debug/test)
- Performance degradate (FindObjectOfType è costoso O(n))

Distribuzione:
- File Critici (Core/UI): ~15 occorrenze → DA MIGRARE
- File Debug/Test: ~20 occorrenze → Accettabili (non in produzione)
- File UI Minigame: ~15 occorrenze → DA MIGRARE GRADUALMENTE
- File Legacy: ~10 occorrenze → DA REFACTORIZZARE
- File World/Systems: ~15 occorrenze → DA MIGRARE

File Prioritari da Migrare:
1. DayCycleController.cs (6 occorrenze)
2. ElevatorSystem.cs (4 occorrenze, parzialmente migrato)
3. PotActions.cs (3 occorrenze)
4. PlayerClickMover2D.cs (1 occorrenza)
5. UI Minigame files (~15 occorrenze totali)

Impatto:
- ⚠️ Performance: FindObjectOfType è O(n) e costoso
- ⚠️ Accoppiamento: Forte dipendenza da GameObject in scena
- ⚠️ Testabilità: Difficile testare isolatamente

Soluzione:
- Migrare a ServiceContainer.Get<T>()
- Implementare late binding dove necessario
- Verificare timing inizializzazione

2. DEBUG.LOG NON OTTIMIZZATI
-----------------------------
Situazione:
- 400 Debug.Log in 41 file
- Solo alcuni wrappati con #if UNITY_EDITOR
- Log verbosi in produzione

Impatto:
- ⚠️ Performance minima in build (ma presente)
- ⚠️ Console verbosa
- ⚠️ Difficile debugging

File Prioritari:
1. UI Components (PotHUDWidget, PotDetailsWidget, etc.)
2. Core Systems (parzialmente fatto)
3. Dome/World Systems

Soluzione:
- Wrappare Debug.Log con #if UNITY_EDITOR
- Implementare sistema logging con livelli
- Mantenere solo log critici in produzione

3. GETCOMPONENT NON CACHED
--------------------------
Situazione:
- 153 occorrenze in 48 file
- Alcuni chiamati ogni frame in Update()
- ~20 occorrenze critiche (chiamate frequenti)

File Prioritari:
1. HUDInventory.cs (12 occorrenze, alcuni in Update)
2. PotDetailsWidget.cs (16 occorrenze)
3. PotHUDWidget.cs (32 occorrenze)
4. HUDPhDisplay.cs (5 occorrenze)

Impatto:
- ⚠️ Performance: GetComponent è costoso se chiamato ogni frame
- ⚠️ Garbage Collection: Possibile allocazione

Soluzione:
- Cache GetComponent in Awake/Start
- Usare RequireComponent dove possibile
- Verificare Update() per chiamate non necessarie

4. UPDATE METHODS ECCESSIVI
----------------------------
Situazione:
- 31 Update/LateUpdate/FixedUpdate
- Alcuni per polling invece di eventi
- Alcuni per input handling (accettabile)

File da Analizzare:
1. PotDetailsWidget.cs (Update per polling UI)
2. HUDInventory.cs (Update per aggiornamenti)
3. HUDPhDisplay.cs (Update per aggiornamenti)
4. PhSystemIdleOscillation.cs (Update per oscillazione)

Raccomandazioni:
- Sostituire polling con eventi dove possibile
- Usare eventi C# o EventSystem invece di Update()
- Mantenere Update() solo per input handling

5. NESSUN TEST UNITARIO
-----------------------
Situazione:
- 0 test unitari
- 0% test coverage
- Difficile verificare regressioni

Impatto:
- ⚠️ Qualità: Difficile garantire correttezza
- ⚠️ Refactoring: Rischioso senza test
- ⚠️ Regressioni: Difficili da individuare

Soluzione:
- Setup Unity Test Framework
- Creare test per sistemi core (ServiceContainer, SaveManager, etc.)
- Implementare test per logica business (PhSystem, EconomySystem)

🟡 PRIORITÀ MEDIA

6. SINGLETON LEGACY
-------------------
Situazione:
- Alcuni singleton ancora usano pattern classico
- AppRoot, PlantDatabase, EventSystem parzialmente migrati

Raccomandazioni:
- Completare migrazione a ServiceContainer
- Rimuovere Singleton Pattern dove non necessario

7. FILE MOLTO LUNGHI
--------------------
Situazione:
- DayCycleController.cs: 1500+ righe
- PhSystem.cs: 700+ righe
- Alcuni metodi >50 righe

Raccomandazioni:
- Dividere file lunghi in più classi
- Estrarre metodi complessi
- Separare responsabilità

8. DIPENDENZE HARDCODED
-----------------------
Situazione:
- ServiceContainer.Instance.Get<T>() direttamente nei costruttori
- Impossibile mockare per test
- Accoppiamento forte a Unity runtime

Raccomandazioni:
- Creare interfacce per sistemi core
- Implementare dependency injection completa
- Permettere mock per test
